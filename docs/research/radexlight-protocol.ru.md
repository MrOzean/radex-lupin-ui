# RADEX LUPIN: исследование RadexLight и протокола обмена

Дата первичного анализа: 2026-11-09  
Исследуемая версия: **RadexLight 1.18.0.0**, сборка от 2024-04-04  
Источник: локальная установка `D:\Apps\radexlight32`

> Документ разделяет подтверждённые наблюдения и гипотезы. До проверки с реальным прибором этот материал нельзя считать полной спецификацией протокола.

## 1. Краткий итог

Перенос основных функций RadexLight в веб-приложение технически выглядит возможным:

- LUPIN использует стандартный USB CDC / виртуальный COM-порт;
- для браузерного подключения подходит Web Serial API;
- низкоуровневый обмен реализован через UART и фирменный протокол Ekosfera RPC;
- поток осциллограммы после синхронизации содержит 32-битные числа с плавающей точкой;
- в RadexLight есть запуск/останов измерений, фильтр, выбор освещённости/яркости, расчёт коэффициента пульсации, спектр, доминирующие частоты, корректирующий множитель и сохранение данных.

После подключения реального прибора подтверждены маркер `OSCILLOSCOPE`, пакеты по 6000 значений и UART 921600 8N1. **Ещё восстанавливаются**: идентификаторы RPC и команды управления режимами. Чтение живой осциллограммы уже реализовано в веб-проекте, но требует браузерной проверки.

## 2. Подключение LUPIN

Подтверждено содержимым `drivers/lupin-usb.inf`:

| Параметр | Значение |
|---|---|
| USB VID | `ABBA` |
| USB PID | `E011` |
| Windows device ID | `USB\VID_ABBA&PID_E011` |
| Класс устройства | `Ports` |
| Системный драйвер | `usbser` через `mdmcpq.inf` |
| Дополнительный компонент | `serenum` |
| Название в диспетчере устройств | `LUPIN` |
| Производитель в INF | `Eco-Electronics` |

Это не проприетарный USB-драйвер передачи данных: используется стандартный Windows USB Serial. Для Web Serial можно применять фильтр:

```ts
const LUPIN_USB = {
  usbVendorId: 0xabba,
  usbProductId: 0xe011,
};
```

Во время первичного анализа прибор не был подключён. После замены кабеля, поддерживающего передачу данных, Windows обнаружила **LUPIN (COM5)**, сервис `usbser`, статус `OK`, `ConfigManagerErrorCode = 0`.

Пассивное открытие COM5 без записи показало, что прибор уже непрерывно передаёт осциллограмму. Пятисекундный захват сохранён в `research/passive-com5.bin` (121 836 байт).

## 4. Поток осциллограммы: подтверждённая часть

В `radexlight.exe` обнаружен класс `EsEapOscProc` с описанием `Oscilloscope input stream processor`.

Полезные виртуальные адреса PE32 (image base `0x400000`):

| VA | Содержимое |
|---|---|
| `0x00BA7290` | Конструктор `EsEapOscProc` |
| `0x00BA74C8` | `contextInit` |
| `0x00BA75AC` | `contextUninit` |
| `0x00BA7C04` | `bufferReadAndParse` |
| `0x00BA7484` | Проверка входного `float` |

Конструктор регистрирует в сервисе три обработчика:

- `contextInit`;
- `contextUninit`;
- `bufferReadAndParse`.

Внутренние поля, видимые по RTTI:

```text
m_svc
m_devChnlAndInfo
m_marker
m_iosc
m_inChunkSize
m_inChunkReadTmo
m_readRetries
m_mul
```

### 4.1. Алгоритм разбора

По машинному коду `bufferReadAndParse` восстановлена следующая последовательность:

1. Прочитать очередной блок из входного канала.
2. При пустом чтении увеличить счётчик повторов и при необходимости сбросить канал.
3. Найти последовательность байтов `m_marker`; поддерживается маркер, разделённый между двумя чтениями.
4. После маркера перейти из состояния синхронизации в разбор данных.
5. Копировать по **4 байта** в локальную переменную типа `Single`.
6. Отбросить значение, если оно NaN, бесконечность или отрицательное.
7. Умножить значение на `m_mul` (корректирующий множитель типа `Double`).
8. Добавить значение в выходной массив осциллограммы.
9. После заполнения ожидаемого количества значений вернуться в состояние готовности/ожидания нового маркера.

На x86 байты последовательно копируются в 32-битную переменную без перестановки, поэтому рабочее представление — **little-endian IEEE 754 binary32**. Это необходимо проверить на живом пакете.

### 4.2. Диагностические строки парсера

В исполняемом файле сохранены сообщения, подтверждающие состояния автомата:

```text
nothing was read from device ... resetting input channel
synchronizing
marker parsed, synchronized -> ParsingData
float input not valid -> Ready -> restartCheck
Full Data received -> Ready
we may continue without an additional read -> restartParsing
retries expired
Exiting with readRetryCnt=...
```

### 4.3. Формат, подтверждённый реальным потоком

В захвате найдены повторяющиеся блоки:

```text
4F 53 43 49 4C 4C 4F 53 43 4F 50 45   O S C I L L O S C O P E
<6000 значений IEEE 754 float32 little-endian>
```

| Параметр | Подтверждённое значение |
|---|---|
| `c_oscMarker` | ASCII `OSCILLOSCOPE`, 12 байт |
| `c_oscPacketSize` | 6000 значений |
| Данные | 24 000 байт |
| Полный блок с маркером | 24 012 байт |
| Частота пакетов | около 1 Гц |
| Частота дискретизации | 6000 отсчётов/с |

Маркеры в файле находятся на позициях 24 336, 48 348, 72 360, 96 372, 120 384 байта. Разница всегда 24 012 байта. Это исключает случайное совпадение.

### 4.4. Что пока неизвестно

- размер чтения `c_oscPacketBuffLen` и число повторов;
- команды входа/выхода из осциллографического режима;
- RPC для идентификации, настроек, яркости и калибровки;
- требуется ли команда для запуска потока из исходного состояния прибора или он продолжает ранее включённый режим.

## 5. Ekosfera RPC и UART

В `esfwx_v1_28_1_vc143.dll` найдены классы и строки, описывающие два уровня обмена.

### 5.1. UART-канал

Объект: `EsChannelIoUart` / `UART direct connection channel`.

Свойства:

```text
port
baud
stopBits
```

Также присутствуют настройки parity, перечисления stop bits и поддержка смены скорости. DLL импортирует Windows API:

```text
CreateFileW
ReadFile
WriteFile
SetCommState
GetCommTimeouts
SetCommTimeouts
SetCommBreak
ClearCommBreak
ClearCommError
SetupComm
PurgeComm
EscapeCommFunction
```

Это подтверждает обычный последовательный канал без дополнительного пользовательского драйвера протокола.

Перехват `SetCommState` официальной программы на реальном COM5 дал:

```text
BaudRate = 921600
ByteSize = 8
Parity   = 0 (NOPARITY)
StopBits = 0 (ONESTOPBIT)
```

При инициализации RadexLight последовательно вызывает `CLRRTS`, `CLRDTR`, затем `SETDTR`, очищает буферы через `PurgeComm(0x0F)`. Итоговые линии: **DTR = true, RTS = false**. В Web Serial после `open()` выставляются те же сигналы.

В полном перехвате двух циклов работы получено 20 622 события, из них 20 588 чтений; **вызовов `WriteFile` к COM5 не было**. Размеры чтения в основном кратны 240 байтам. В первом сеансе прочитано 5 972 364 байта и найдено 249 маркеров, во втором — 312 732 байта и 13 маркеров.

При останове RadexLight очищает буферы и снимает DTR. После этого наблюдается кратковременное открытие на **9600 8N1**, затем при следующем запуске снова 921600. Точная последовательность пробуждения после полного останова ещё проверяется: простая установка DTR вручную не возобновила поток.

### 5.2. RPC поверх Ekosfera

Объект `EsRpcMaster` описан как `RPC master services over Ekosfera protocol`.

Методы и возможности:

```text
activate / deactivate
ping / pingEx
changeAddr
rateSet / currentRateGet
getImplementedRPCs
getHealthInfo / queueHealthCheck
factoryReset
shutdown
queueBootloader
protocolFrameSent
protocolFrameReceived
protocolFrameSendingFailed
protocolFrameReceptionFailed
```

Свойства включают:

```text
monitor
clientAddr
packetTimeout
channel
active
```

Наличие `monitor` и событий отправки/приёма кадров полезно для дальнейшего захвата протокола штатными средствами библиотеки.

Из сообщений об ошибках следует, что в кадрах есть как минимум:

- размер данных;
- команда/RPC ID;
- CRC;
- статус ответа;
- выравнивание некоторых данных по 2 байта.

Подтверждённые диагностические сообщения:

```text
Data size in header does not equal to real data size
Wrong data size alignment (not multiple of 2)
CRC data error
Unknown command
Pending data packet is too long
Actual data size is unexpected for this command
Requested rate value is not supported
Requested device address is out of range
Device is not ready
```

Сигнатуры RPC используют типы `VOID`, `esU8/U16/U32/U64`, `esI8/I16/I32/I64`, `esBL`, `esDT`, `esBA`, `esF`.

## 7. Веб-перенос: возможности и ограничения

### 7.1. Что можно реализовать локально в браузере

- открытие COM-порта по VID/PID;
- приём и отправку бинарных пакетов;
- разбор float32 и кадров Ekosfera после завершения reverse engineering;
- расчёт минимума/максимума/среднего и коэффициента пульсации;
- FFT и список доминирующих частот;
- графики на Canvas;
- запись и экспорт CSV;
- сохранение настроек локально;
- работу без загрузки измерений на сервер.

### 7.2. Ограничение «на любом устройстве»

Web Serial API доступен не везде:

- Chrome/Edge на настольных ОС — основной поддерживаемый вариант;
- Android Chrome — возможен при поддержке USB OTG и совместимости ОС/устройства;
- Safari, Firefox и iOS — нельзя рассчитывать на Web Serial;
- страница должна работать в secure context: HTTPS или `localhost`.

Для полностью универсального варианта позже можно добавить маленький локальный bridge на Node.js/Python, но это уже не чистый Web Serial.

## 11. Текущий статус веб-проекта

Создан каркас Vite + TypeScript, нативный Web Serial transport, демонстрационный источник, расчёт статистики/FFT, Canvas-графики, CSV-запись и hex-журнал диагностики.

Добавлен инкрементальный `LupinStreamParser`: ищет `OSCILLOSCOPE`, дожидается полного блока, читает 6000 float32 LE и выдаёт пакет в интерфейс с частотой 6000 Гц. Поддерживаются частичные чтения и маркер на границе двух чтений.

### 11.1. Автоматическая проверка парсера

`research/test_parser.ts` читает реальный `passive-com5.bin`, подаёт данные неравными фрагментами и проверяет четыре полных пакета:

```powershell
npx --yes tsx research\test_parser.ts
```

Результат первого пакета: min `2.7582073`, max `2.8121848`, mean `2.7855765`, пульсация `1.93775%`.

### 11.2. Спектр и цифровой фильтр

По коду `EsEapMath.normalizeAndExtremaFind` и `EsMathArrayComplex.modulusOfLengthGet` восстановлена обработка спектра:

- FFT выполняется по всем 6000 отсчётам пакета;
- вычисляются модули комплексных FFT-отсчётов и их общая сумма;
- каждый бин нормируется на эту сумму;
- отображаемая величина — `20 * log10(magnitude / sum)`;
- максимум не поднимается принудительно к 0 дБ;
- результат содержит `N/2 + 1` бинов, то есть полный диапазон 0…3000 Гц;
- доминирующие частоты выбираются по локальным пикам выше −40 дБ.

Для произвольной длины 6000 используется Bluestein FFT + radix-2. `research/test_fft.ts` проверяет результат против наивного DFT на длинах 5, 12 и 16 и контрольный сигнал 100 Гц.

В настройках RadexLight обнаружено `ApplyFilter = 1`. В веб-интерфейс добавлен переключаемый FIR windowed-sinc НЧ-фильтр 500 Гц (101 tap, Blackman), состояние которого сохраняется между пакетами. Он визуально приближен к поведению оригинала, но бит-в-бит идентичность коэффициентов фильтра пока не доказана.

### 11.3. Проверка Web Serial на реальном приборе

В Chrome после выбора LUPIN (COM5) интерфейс показал правдоподобные живые данные:

- обычный источник: около `147 лк`, пульсация `1.2–1.8%`, пик `100 Гц`;
- закрытый датчик: около `0.6 лк`, низкочастотный шум без значимого светового сигнала;
- фонарик: рост до `480 лк`, доминирующая частота около `400 Гц`, вероятно от его драйвера.

Это подтверждает работу сквозного пути **USB CDC → Web Serial → синхронизация по маркеру → float32 → статистика → FFT**.

Первый вариант интерфейса мог зависать из-за неограниченного HEX-журнала мелких RX-чтений. Исправлено: журнал группируется раз в 150 мс и ограничен последними 200 строками. Последующий soak-тест в Chrome прошёл около 20 минут без зависаний; память вкладки оставалась около 15 МБ с периодической нормальной работой GC.

### 11.4. BPULSE: первичный разбор (2026-11-12)

Для известного unpacked-представления RadexLight 1.18 реализован `research/analyze_bpulse.py`. Формат содержит сериализованное дерево `ROOT → EAP`, строки `DeviceType`, `DeviceCalibration`, `LUPIN01_FwInfo`, `Mode` и массив `EsMathArrayReal`. Каждый элемент массива записан как отдельная структура с двумя индексами `IDX` и значением float32 LE; шаг полной записи — 55 байт, последняя запись файла завершается сразу после значения.

Из обоих имеющихся файлов извлечены ровно 6000 отсчётов и метаданные:

- `DeviceType = 60002`;
- `f_order = 1592`;
- дата firmware `2017-05-15`;
- версия firmware `1.3`;
- `countryCode = 643`.

Отчёт и хэши массивов: `research/bpulse-analysis.json`. Поля `lumDiv` в этом представлении нет. Существующие файлы with/without filter являются разными захватами, поэтому не образуют синхронную пару для бит-в-бит проверки FIR. Исходные упакованные `.bpulse` пока не найдены; универсальная поддержка формата не заявляется.

### 11.5. Расширенный захват UART

`capture_official.py` больше не перезаписывает исходный журнал: каждый запуск создаёт `official-serial-<timestamp>.jsonl`. Перехват записи расширен на `kernelbase!WriteFile` и `WriteFileEx`, поскольку в исходном журнале было 14714 чтений и ни одной записи через `kernel32!WriteFile`.
